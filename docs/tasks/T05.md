## Goal

Add an accessible See more control that expands the price table from its initial five usable quantity rows to every usable row already present in the current response, without fetching again, and collapses the table immediately when a different paper size is applied.

## Inspection and dependency evidence

- `PriceTable` currently filters empty rows and unconditionally slices the usable rows to five. It already maps cells by quantity and business day and needs only a presentation input that controls the row limit.

## Acceptance criteria

1. A response with more than five usable quantity rows initially renders exactly the first five usable rows in response order.
2. When additional usable rows exist, an accessible control named `See more` appears with the current table and can be activated by pointer or keyboard.
3. Activating See more reveals every usable loaded row, including all ten rows in the specified API response, and the newly visible cells retain the existing semantic, formatting, unavailable-cell, and selection behavior.
4. Expansion uses only the current response. It does not call `fetchPrices`, request another page, retry, or otherwise initiate network work.
5. After all usable rows are visible, See more is no longer offered because there are no additional rows to reveal.
6. Responses with five or fewer usable rows render every usable row and do not show See more.
7. Draft-only selector changes and same-size Apply preserve the current expansion state and make no request.
8. Applying a different paper size collapses the table immediately. After that response resolves, the new table initially shows at most five usable rows and offers See more only when additional rows exist.
9. The control uses native button semantics, has an understandable accessible name, supports Enter and Space, and has a visible keyboard-focus style at desktop and narrow widths.
10. T05 does not change API pagination, request lifecycle, response ordering, selection clearing, Order price rules, hover behavior, Cart behavior, routing, global state, backend behavior, or production error fallback.
11. Controlled automated tests cover ten-row expansion, no additional request, keyboard activation, control visibility for short/exhausted data, and reset/preservation behavior across draft, same-size, and different-size Apply transitions without using the live API.
12. The final diff is scoped; acceptance criteria and the task diff are inspected; focused/full tests, formatting, lint, and build pass; real latest Chrome or Firefox verifies expansion, reset, focus, selection in expanded rows, and responsive layout.

## Implementation assumptions

These are task-level choices, separate from assignment requirements:

- Keep a boolean `showAllRows` in `App`, initialized to `false`, because `App` already owns different-size Apply transitions.
- In the existing different-size Apply branch, clear selection and set `showAllRows` to `false` before updating the applied size. Draft-only changes and same-size Apply do not collapse expansion.
- Pass the expansion flag and an expansion callback to `PriceTable`, keeping row derivation next to the table rendering.
- Define usable rows as non-empty response rows, matching the existing empty-state and table logic. See more appears only when that filtered collection has more than five rows and the table is collapsed.
- See more reveals all usable rows in one action; it is not a toggle. Remove the control after expansion rather than introducing unspecified See less behavior.
- Render the button adjacent to the table in the same presentational component so its visibility is derived directly from the rows it controls. Use `aria-controls` only if a stable table identifier is added cleanly; native button text and proximity remain the primary accessible relationship.
- Preserve selected cells during expansion. A cell selected in an expanded row continues to drive Order price; the already-specified different-size Apply reset clears it together with expansion.

## Risks and blockers

- Counting raw response rows would make empty rows consume the five-row allowance. Reuse the existing usable-row filtering before slicing and determining control visibility.
- Owning expansion only inside `PriceTable` would make a different-size reset effect-dependent and could briefly retain expanded state. Reset it synchronously in the App Apply transition.
- A See more button placed in the paper-size form could accidentally submit and fetch. Keep it outside that form and explicitly use `type="button"`.
- Selection identity must remain based on quantity and business day when rows become visible; expansion must not introduce index-based identity.
- CSS around a control beneath a horizontally scrollable table can accidentally widen the page. Verify the scroll container and narrow viewport in a real browser.
- The missing reference image prevents exact visual comparison; requirements-based browser QA remains required.
- Existing unstaged prior-task shipping records overlap `docs/plan.md`. Preserve their hunks and stage only T05-owned content during shipping.

No unresolved blocker prevents implementation.
