## Goal

Implement a small, reusable TypeScript function that formats positive integer prices with comma separators between groups of three digits counted from the right, and prove its required behavior with focused unit tests.

## Acceptance criteria

1. A reusable TypeScript formatter accepts a price in the assignment's positive-integer domain and returns its base-10 digits with commas between every group of three digits counted from the right.
2. Values with one to three digits are returned without a separator.
3. The formatter handles the first separator boundary and values that require multiple separators.
4. The implementation does not use `toLocaleString()`, `Intl.NumberFormat()`, jQuery, Lodash, Underscore, or another formatting/utility dependency.
5. Focused Vitest unit tests cover no-separator values, the 999-to-1,000 boundary, a value with a non-full leading group, and at least one value requiring multiple separators.
6. The existing formatting check, lint, full unit-test command, and production build pass without weakening configuration or unrelated tests.

## Scope and non-goals

## Implementation assumptions

These are task-level choices, separate from assignment requirements:

- Add a named export `formatPrice(price: number): string` in `src/utils/formatPrice.ts`. A named export makes later consumers and tests explicit without introducing a broader utility abstraction.
- Convert the valid integer to its ordinary decimal string and insert separators based on distance from the right. Keep the algorithm directly inspectable and free of locale-sensitive APIs.
- Place the test at `src/utils/formatPrice.test.ts`, next to the module it verifies, and use explicit imports from Vitest because test globals are intentionally disabled.
- Test representative valid-domain values rather than inventing undocumented error or coercion behavior.

## Risks and blockers

- JavaScript numbers outside the safe-integer range can lose decimal precision before the formatter receives them. The assignment only states positive integers and supplies no large-price or arbitrary-precision requirement, so T01 will not introduce `bigint` or string-input behavior without a requirement change.
- Over-generalizing validation could establish undocumented behavior that later consumers accidentally rely on. Keep implementation and tests within the stated positive-integer domain.
- A separator algorithm can accidentally group from the left; the `12_345` case specifically protects right-based grouping.
- PowerShell may block the ordinary npm shim in this environment. Use the already-verified `npm.cmd` commands without changing machine policy.
- The sandbox process startup limitation recorded in T00 may recur. If it does, report it accurately and use only approved execution paths; do not alter machine or sandbox configuration.

There are no unresolved product inputs or dependency blockers for implementation.
