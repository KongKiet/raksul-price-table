## Acceptance criteria

1. On initial render, the application requests A4 from `https://us-central1-fe-ws-test.cloudfunctions.net/prices?paper_size=A4` through a dedicated API module using native `fetch` and an `AbortSignal`.
2. Request ownership is guarded so an aborted or superseded request cannot update current data, error, or loading state in success, failure, or completion paths.
3. While the current request is pending, the UI presents an understandable loading state and does not show stale table or error content.
4. A successful non-empty response renders a semantic price table with a caption, column headers for delivery business days, row headers for quantity, and formatted price cells.
5. Business-day columns are derived from all returned entries, deduplicated, and sorted numerically. Each row's entries are matched to columns by `business_day`, never by array position.
6. Only the first five loaded quantity rows are visible. If fewer than five rows are returned, all available rows are shown. No pagination or follow-up fetch is introduced.
7. A missing quantity/business-day combination is rendered as unavailable rather than borrowing a neighboring or positional value.
8. Prices are rendered with T01's `formatPrice` function. The mandatory formatter unit tests remain present and passing.
9. A failed request displays an understandable error state and accessible Retry control. Retry starts a new A4 request and can recover to the table; production failure never falls back to fixture or mock data.
10. A successful response with no usable price rows displays an understandable empty state rather than an empty table.
11. Automated tests use controlled mocks or fixtures and verify loading, success mapping, numeric column ordering, five-row limiting, unavailable combinations, error, retry recovery, empty data, and stale-request protection without calling the live API.
12. The task diff is scoped, formatting, lint, tests, and the production build pass, and the rendered states and responsive table are verified in a real latest Chrome or Firefox browser.

## Implementation assumptions

These are task-level implementation choices, separate from assignment requirements:

- Define a small API module at `src/api/prices.ts`. It owns the endpoint, request construction, response types, HTTP failure handling, and runtime validation needed to prevent malformed data from reaching presentation.
- Represent paper sizes with the documented `A4 | A5 | B4 | B5` union so the API boundary will support T03 without implementing a selector now. T02 always calls it with `A4`.
- Keep request lifecycle state in a focused hook at `src/hooks/usePrices.ts`. Track the latest request identity as well as its `AbortController`; every state write, including `finally` loading cleanup, must verify current ownership. Abort on supersession and unmount. Treat an abort as cancellation, not a user-facing error.
- Keep `PriceTable` presentational. Derive columns and cell lookup from its response data with deterministic helpers instead of coupling rendering to fetch state.
- A usable row contains at least one valid entry, and its quantity comes from that entry. A response with no usable rows is empty. A malformed contract is an error rather than silently repaired fixture data.
- Preserve API row order because the contract states rows are already sorted by increasing quantity. Derive and numerically sort only business-day columns.
- Display an em dash for unavailable combinations and include understandable accessible text for that state. Exact copy and styling may be refined during implementation while preserving observable semantics.
- Replace the starter-specific global styling with a neutral page foundation and use CSS Modules for application/table styles. Remove `src/App.css` after its import is eliminated; leave unrelated static assets alone unless a scoped cleanup is clearly necessary.
- Do not expose raw technical error details to users. Tests may assert a stable user-facing message while task evidence records the concrete failure.

## Risks and blockers

- The production endpoint and response were transcribed from user-provided requirements and have not been independently fetched. Runtime validation and explicit error UI contain contract/network failures; automated tests remain controlled.
- React Strict Mode deliberately exercises effect setup and cleanup twice in development. A controller alone is insufficient if a mocked or already-completing request ignores cancellation, so request-identity checks must guard every state write.
- The two-dimensional response can contain entries in different orders or omit combinations. Positional rendering would show incorrect prices; the mapping tests must use deliberately shuffled and sparse rows.
- The reference image is missing, so exact visual comparison cannot be completed. Requirements-based real-browser verification is still mandatory and must not claim reference parity.
- Responsive tables can become unreadable if forced to shrink. Prefer a labeled horizontal scroll region while retaining table semantics and visible focus.
- Current T00/T01 post-commit evidence is uncommitted and outside T02 scope. Preserve it; do not overwrite, stage, or attribute it to T02 without explicit authorization.

No unresolved blocker prevents implementation. A live endpoint outage may limit production-data browser observation but must surface as the specified error state, never trigger mock fallback, and must be recorded honestly.
